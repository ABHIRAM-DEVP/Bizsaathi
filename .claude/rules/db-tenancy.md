# Database and tenancy rules
- PostgreSQL is the source of truth for prices, stock, confirmed product facts, orders, approvals and audit events.
- Every business-owned table has `business_id`. Repositories take the tenant from the authenticated context and always filter on it. Consider Postgres row-level security as a second boundary (ADR first).
- Cross-tenant negative tests are required for every new resource: tenant B cannot read, update, delete or reference tenant A's rows by id.
- Alembic only. Never edit an applied or merged migration; add a new one. Read the autogenerated file, check downgrade, test on real Postgres.
- Confirmed facts and AI suggestions live in different columns or tables. A suggestion becomes a fact only through an explicit seller-approved write.
- Order status is a state machine (DRAFT -> AWAITING_PAYMENT -> PAID -> FULFILLED, plus cancel/failure). Only the execution service writes status; never a model, never a node.
- Evidence records reference product id, stock version, policy version and source span so claims are traceable.
- Idempotency keys on order creation, approvals and notifications. Timestamps are timestamptz UTC.
- Integration tests use real Postgres (Testcontainers or compose), never SQLite.
